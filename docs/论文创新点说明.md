# WFCLLM 论文创新点说明

> 这份文档面向第一次接触 WFCLLM 的读者。它不要求读者了解代码水印、代码大模型或统计检测。

## 1. 一句话介绍我们的工作

WFCLLM 把代码水印从“控制模型更常使用哪些词”推进到“控制模型生成怎样的代码结构和语义表达”，并让检测者只看最终代码就能寻找水印证据。

更完整的一句话是：

> 我们在代码生成过程中，以完整的代码结构为边界，用密钥引导模型寻找符合要求的语义表达；检测时再从最终代码中重建同一套证据，不需要知道当时使用了什么提示词，也不需要读取生成日志。

## 2. 什么是代码水印

代码水印不是在代码里插入作者名字、特殊注释或固定字符串。那样的标记太明显，也很容易被删除。

我们研究的是一种不可见的统计水印。它不会要求每段代码都出现某个固定标记，而是让大量受控生成的代码在某些特征上更倾向于密钥指定的区域。只有知道密钥并使用相应检测方法的人，才能判断这种倾向是否明显。

可以把它理解成一枚“看不见的印章”：普通读者看到的仍然是正常代码，检测者看到的却是一组可以累积的秘密证据。

## 3. 现有思路面临的主要问题

许多生成时水印直接控制 token，也就是模型逐步生成的词、符号和代码片段。例如，密钥可以让模型更倾向于选择某一组候选 token。

这种方法容易实现，也能在一段代码里留下较多证据，但它与代码表面写法绑定得很紧。一段功能不变的代码，可以有很多不同写法：

- 变量 `count` 可以改成 `n`；
- 单引号可以改成双引号；
- 表达式可以换成等价写法；
- 一个循环可以改成列表推导式；
- 代码可以被格式化、重排或局部重构。

这些修改可能不影响程序功能，却会大量改变 token。于是，一个只依赖表面词语的水印可能明显减弱。

另一些方法在检测时还需要原始提示词、生成模型或生成过程中的概率信息。这些信息在真实传播场景中未必能够保留。代码被复制到仓库、论坛或作业系统后，检测者通常只能拿到最终文件。

因此，我们真正想解决的不是“怎样再增加一种 token 偏置”，而是下面这个问题：

> 能不能让水印依附在比 token 更稳定的代码单位上，并让最终代码本身成为完整的检测证据？

## 4. 我们的核心故事

WFCLLM 的核心不是某一个孤立技巧，而是一条首尾一致的设计路线：

1. 代码天然有结构，因此以完整语句或语句组为处理边界，而不是在任意 token 位置做决定。
2. 同一功能通常有多种写法，因此让模型在生成过程中寻找满足秘密语义条件的写法。
3. 检测者只拿到最终代码，因此嵌入和检测必须使用能够从最终代码重新计算的证据。
4. 代码可能被局部修改，因此水印证据应尽量分散在多个结构单元中，而不是依赖一个特殊片段。

这条路线可以概括为：

> 结构决定在哪里放水印，语义决定什么样的写法算命中，密钥决定秘密目标，最终代码负责保存并重现证据。

## 5. 创新点一：用“结构语义单元”承载水印

这是论文最应该突出的主创新。

传统生成时水印通常在模型每生成一个 token 时施加偏向。WFCLLM 则先等待一个有意义的代码单位生成完整，例如一个赋值、一个返回语句，或由少量语句组成的局部窗口，再判断这个整体是否携带水印证据。

系统会把这个代码单位转换成一个表示其语义和结构的向量。密钥把向量空间划分出一组秘密的“目标区域”。如果当前代码单位落入目标区域，就视为一次水印命中。

这个设计带来 3 个重要变化：

- 水印的基本单位从“某个词”变成“一个有意义的代码片段”；
- 水印选择与代码结构对齐，不会在任意位置生硬地干预生成；
- 水印更有机会保留在功能不变、表面写法发生变化的代码中。

这里最重要的论文表达不是“我们使用了 AST”或“我们使用了 LSH”。AST 只是代码结构的表示方式，LSH 只是划分语义区域的工具。真正的创新主张是：

> 我们提出了一种以代码结构划定边界、以语义区域承载秘密偏向的生成时代码水印方式。

## 6. 创新点二：在生成过程中通过“回退再生成”寻找水印表达

知道水印应该放在哪些结构单元里，还需要解决一个问题：怎样让模型生成的代码单位进入密钥指定的目标区域？

WFCLLM 使用一种直观的搜索方法：

1. 模型先正常生成一个完整代码单位；
2. 系统判断它是否命中秘密目标区域；
3. 命中就保留，继续向后生成；
4. 没命中就回退到这个单位开始之前，换一个随机种子重新生成；
5. 达到重试上限后停止搜索，避免成本无限增加。

这类似于让模型做几次不同的表达尝试，然后只根据水印证据选择更合适的版本。

它与简单的 token 概率偏置不同。系统不需要在每一步强行修改模型的候选词分布，而是在完整结构边界上判断一次“这个表达是否符合秘密条件”。因此，水印控制发生在更接近程序结构和语义的层面。

当前系统还可以进行多次完整生成，并按照水印证据选择一个结果。选择过程只看水印命中情况，不看单元测试是否通过，也不借助答案正确性。这让实验能够更清楚地回答：检测提升是否确实来自水印机制，而不是偷偷挑选了更容易通过测试的代码。

## 7. 创新点三：最终代码自身就是检测证据

这是 WFCLLM 最重要的实际价值之一。

检测时，系统只分析最终代码内容：重新解析代码结构，切分出可以检测的代码单位，计算语义表示，再用相同密钥重建目标区域并统计命中情况。

检测过程不需要：

- 生成模型当时看到的提示词内容；
- 生成模型的内部概率；
- 每一步生成了哪些候选 token；
- 哪些代码单位曾经被回退；
- 生成日志、缓存或候选版本；
- 单元测试结果或答案正确性。

这意味着代码离开原始生成环境后，仍然可以独立检测。例如，代码被复制到 Git 仓库后，检测者只要获得最终文件和密钥，就可以运行检测。

需要准确表述的是：当前官方数据文件为了记录样本来源，仍保留一个 `prompt` 字段；但是检测实现不会读取该字段的内容，结构提取时固定按 `prompt=None` 处理。因此论文中适合写“检测不依赖 prompt 内容”，而不是写“输入格式中不存在 prompt 字段”。

“只看最终代码”本身并不是所有代码水印中从未出现过的能力。我们的差异在于，它与“结构对齐的语义载体”和“生成时回退搜索”组成了一个闭环：生成端留下的证据，检测端能够仅凭最终代码按同一规则重建。

## 8. 创新点四：生成与检测使用同一套结构语义规则

一个水印系统常见的隐患是：生成端认为自己嵌入了证据，但检测端从最终代码里找不到相同证据。原因可能是两端切分代码的方式不同、使用的上下文不同，或者密钥定位规则不一致。

WFCLLM 的设计目标是让两端围绕同一条证据链工作：

```text
最终代码
  → 找到结构单元
  → 计算语义表示
  → 根据结构和密钥重建目标区域
  → 统计命中证据
```

生成端用这条链路决定是否回退，检测端用同一条链路判断是否存在水印。这样，系统不是在生成后额外猜测“哪里可能有水印”，而是从一开始就要求水印证据能够被最终代码重建。

这可以被概括为一种“自包含证据闭环”：生成过程负责把证据写入最终产物，检测过程只从最终产物读回证据。

## 9. 创新点五：面向等价改写的潜在鲁棒性

代码水印的鲁棒性，是指代码经过修改后，水印仍然可以被检测到。WFCLLM 的鲁棒性潜力来自 3 层设计。

第一层是语义表示。系统希望把功能相同、写法不同的代码映射到相近位置。例如变量重命名或格式变化后，语义表示不应发生剧烈变化。

第二层是结构边界。水印证据分布在多个代码单位中。局部修改通常只会影响附近的若干证据，而不一定破坏整段代码的全部水印。

第三层是统计汇总。检测不是依赖某一个固定片段，而是汇总多个结构单元的命中情况。只要保留下来的证据仍然足够多，整体判断就可能保持稳定。

因此，我们应该把鲁棒性讲成一个有明确来源的机制主张，而不是一句笼统的“我们更鲁棒”：

> 由于水印绑定的是结构对齐的语义区域，而不是具体 token，WFCLLM 预期能够更好地承受格式化、重命名和一部分功能不变的代码改写；局部编辑造成的影响也有机会被限制在局部结构单元内。

这个创新点的说服力最终取决于系统化改写实验，具体方案见配套文档《创新点验证实验计划（通俗版）》。

## 10. 支撑特点：证据不足时允许“不作判断”

短代码可能只包含很少几个可检测的结构单元。如果证据数量太少，系统不会强行给出肯定结论，而会标记为“证据不足”。

这不是最主要的算法创新，但它让检测结果更诚实，也更适合真实应用。一个可靠的检测器不仅要会判断“有水印”和“无水印”，还要能区分“没有水印”与“这段代码太短，暂时无法判断”。

## 11. 支撑特点：不使用代码正确性来控制水印选择

WFCLLM 在生成、回退、候选选择、阈值确定和检测过程中，都不使用单元测试结果或答案正确性作为控制信号。

这样做有两方面价值：

- 实际使用时不要求每个任务都提前准备测试用例；
- 研究评测时可以避免把“挑中了正确答案”误当成“水印机制更有效”。

代码质量仍然需要在全部生成和检测结束后单独测量，但它只是结果报告，不参与水印决策。

## 12. 创新点之间是什么关系

这几项贡献不是互相独立的功能堆叠，而是一条因果链：

```text
token 水印容易被表面改写影响
  ↓
把水印单位提升到结构对齐的语义片段
  ↓
用回退再生成搜索符合密钥要求的表达
  ↓
让生成端和检测端使用同一套证据规则
  ↓
最终只凭代码重建证据，并获得抗局部改写的潜力
```

因此，论文不宜把所有特点平铺成同等重要的 6 个创新点。推荐采用“1 个主创新 + 3 个支撑贡献”的结构：

### 主创新

提出一种结构对齐的生成时语义代码水印：以完整代码结构单元为边界，以密钥指定的语义区域承载水印。

### 支撑贡献一

设计可回退的语义搜索机制，使模型能够在生成过程中寻找满足水印条件的表达，而不是只在 token 层修改概率。

### 支撑贡献二

建立生成与检测一致的证据闭环，使检测能够仅从最终代码重建水印，不依赖 prompt 内容、生成模型或生成日志。

### 支撑贡献三

利用语义表示、结构分散和统计汇总，使水印具有抵抗表面改写和局部编辑的机制基础，并通过分层改写实验验证这种鲁棒性。

## 13. 论文应该怎样讲这个故事

推荐的叙事重点不是“我们在干净代码上的检测数字最高”，而是解决一个更完整的问题：

> 如何在不依赖生成过程信息的条件下，让代码水印既能在生成时写入，又能从最终代码独立读出，并尽量不被功能不变的表面改写轻易破坏？

围绕这个问题，论文可以依次讲：

1. token 水印的证据密集，但容易随表面写法变化；
2. 真实检测通常只能获得最终代码；
3. WFCLLM 用结构语义单元替代任意 token 位置作为水印载体；
4. 用回退再生成实现生成时语义搜索；
5. 用同一密钥和同一结构规则从最终代码重建证据；
6. 最后用干净检测、代码质量、改写鲁棒性和运行成本共同评价方法。

这会把论文从“又一个水印打分器”提升为“生成、承载、保存和检测水印证据的一体化方法”。

## 14. 可直接用于论文讨论的简短版本

### 版本 A：最简洁

> WFCLLM 将生成时代码水印从 token 级概率偏置提升到结构对齐的语义区域搜索。它在完整代码单元闭合时检查水印证据，必要时回退并重新生成；检测端仅凭最终代码和密钥重建同一证据，因此不依赖 prompt 内容、生成模型或生成日志。

### 版本 B：突出鲁棒性

> WFCLLM 不是把水印绑定到具体 token，而是绑定到代码结构中的语义单元。生成端通过回退搜索满足密钥条件的表达，检测端从最终代码重建这些语义证据。由于证据跨多个结构单元分布，该方法有望比纯 token 水印更能承受格式化、重命名和局部等价改写。

### 版本 C：突出实际使用

> WFCLLM 把最终代码视为自包含的水印证据。代码一旦离开生成环境，检测者仍可只使用代码和密钥完成判断，不需要保存原始 prompt、模型概率、重试记录或测试结果。

## 15. 最终建议

论文的核心标签建议固定为：

> **结构对齐、生成时语义搜索、最终代码独立检测。**

鲁棒性是这条路线最有价值的结果之一，但它应该被解释为上述机制自然带来的能力，并用专门实验进行验证。这样，创新点既不会停留在“用了 AST、用了编码器、用了 LSH”的零件层，也不会夸大为未经拆解的“全面鲁棒”，而是形成一条清楚、可验证、容易记住的研究故事。
