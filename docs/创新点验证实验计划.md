# WFCLLM 创新点验证实验计划

> 这份文档回答一个直接问题：为了让不了解项目的论文审稿人相信我们的创新点，还需要补哪些实验？

## 1. 实验不是越多越好

论文实验的目标不是展示系统有多少开关，而是建立一条完整证据链：

1. 水印确实被写进了最终代码；
2. 检测者只看最终代码也能把它读出来；
3. 检测效果确实来自结构语义机制，而不是重试次数、更多计算或挑选正确答案；
4. 代码经过功能不变的修改后，水印比纯 token 方法保留得更好；
5. 这种能力没有以明显破坏代码质量或不可接受的生成成本为代价。

所有实验都应围绕这 5 个问题服务。不能改变读者判断的实验，可以不放在主论文里。

## 2. 先固定论文要证明的主张

建议只保留 1 个主要主张和 1 个辅助主张。

### 主要主张

> 结构对齐的语义水印可以在生成时写入，并且能够只从最终代码中重新检测。

### 辅助主张

> 与只绑定表面 token 的水印相比，这种水印更有机会在功能不变的代码改写后保留，同时维持可接受的代码质量和生成成本。

### 必须排除的替代解释

实验还要排除下面几种质疑：

- 检测器其实暗中使用了 prompt；
- 检测提升只是因为同一个问题生成了更多候选；
- 提升来自测试用例筛选，而不是水印机制；
- 结构切分和语义表示没有作用，普通 token 方法同样能做到；
- 鲁棒性只是因为改写太弱，或者改写后代码已经不能运行；
- 检测器只记住了 HumanEval 或某个生成模型的风格。

## 3. 读懂实验需要知道的 5 个指标

为了让文档容易阅读，这里先用日常语言解释常用指标。

### 检出率

在真正含水印的代码中，有多少被成功识别。越高越好。

### 误报率

在没有水印的代码中，有多少被错误识别为含水印。越低越好。

论文建议重点报告“误报率固定为 5% 时的检出率”，这样所有方法在同样严格的误报条件下比较。

### AUROC

它衡量检测器区分“有水印”和“无水印”的整体能力。`0.5` 接近随机猜测，越接近 `1.0` 越好。它适合看整体趋势，但不能替代固定误报率下的检出率。

### pass@1

模型第一次生成的代码中，有多少能通过任务测试。它用来检查水印是否破坏代码质量。代码质量测量必须在生成和水印选择全部完成后进行，不能反过来参与候选选择。

### 水印保留率

代码被修改后，检测分数还保留了多少。可以同时报告分数保留比例和修改后的检出率。只报告其中一个容易造成误解。

## 4. 主张与实验的对应关系

| 要证明的事情 | 最关键的实验 | 建议位置 |
| --- | --- | --- |
| 生成端写入的证据能被检测端读回 | 生成—检测一致性实验 | 主论文 |
| 干净代码上能够检测 | 主要检测对比实验 | 主论文 |
| 检测不依赖 prompt 内容 | prompt 替换与删除实验 | 主论文或附录中的硬性检查 |
| 结构语义设计确实有用 | 组件删除实验 | 主论文 |
| 对等价改写更稳定 | 分层鲁棒性实验 | 主论文核心图表 |
| 没有明显破坏代码质量 | pass@1 与语法正确率实验 | 主论文 |
| 成本仍然可接受 | 重试次数、生成时间和 token 成本实验 | 主论文或附录 |
| 不是只对一个模型或数据集有效 | 跨模型、跨数据集实验 | 主论文或附录 |
| 证据不足的判断是合理的 | 按代码长度和证据数量分组实验 | 附录，可在正文简述 |
| 密钥确实提供了区分能力 | 错误密钥和伪造实验 | 附录，安全讨论必备 |

## 5. 必做实验一：生成—检测一致性

这是所有后续实验的地基，优先级最高。

### 想证明什么

生成时被系统认为“命中”的结构语义证据，确实能从最终保存的代码中重新找到。否则，即使生成日志显示水印很多，最终检测也可能没有意义。

### 怎么做

对每个生成样本，同时保存两类信息：

- 生成阶段记录的结构单元和水印命中；
- 检测阶段只从最终代码重新提取的结构单元和命中。

然后逐个比较：

- 两端找到的结构单元是否对应；
- 对应单元的父结构是否一致；
- 用同一密钥得到的目标区域是否一致；
- 生成时的命中能有多少在最终检测中重现；
- 哪些证据因为代码未完整闭合、结构解析失败或窗口切分不同而丢失。

### 需要报告什么

- 结构单元对齐率；
- 目标区域重建一致率；
- 生成命中在最终代码中的重现率；
- 每类丢失原因的比例；
- 按代码长度、结构类型和重试层级分组的结果。

### 什么结果有说服力

两端对同一最终代码的结构切分和密钥目标应高度一致。无法重现的证据必须能归入清楚、可统计的原因，而不是大量“未知丢失”。

### 如果结果不好，说明什么

说明当前最先需要修复的是嵌入与提取不一致，而不是继续调检测阈值。没有这项一致性，其他性能实验很难解释。

## 6. 必做实验二：干净代码上的主要检测对比

### 想证明什么

在代码没有被攻击或改写时，WFCLLM 能把含水印代码与普通代码区分开。

### 怎么做

至少准备 3 组代码：

1. 使用 WFCLLM 生成的含水印代码；
2. 同一生成模型、同一任务、相近生成参数得到的无水印代码；
3. 其他模型生成或人类编写的代码，作为更真实的负样本。

比较方法控制在 3 类以内：

- 一个有代表性的 token 生成时水印；
- 一个已有的代码专用水印；
- WFCLLM。

如果某个对比方法检测时需要 prompt 或原生成模型，应按它的正式设置给足所需信息，同时在表中明确标注。不要故意削弱对比方法。

### 需要报告什么

- 误报率固定为 1% 和 5% 时的检出率；
- AUROC；
- 被标记为“证据不足”的样本比例；
- 不同代码长度下的检出率；
- 在 HumanEval、MBPP 等数据集上的分别结果。

### 什么结果有说服力

最理想的结果是 WFCLLM 在干净代码上达到或超过强基线，并在改写后明显领先。

如果干净检测略低于 token 基线，也仍然可以形成论文故事，但必须同时满足：

- 干净代码上的差距不大；
- 改写后的水印保留明显更好；
- 检测只需最终代码，使用条件更少；
- 代码质量和成本仍在可接受范围内。

因此，论文应比较完整的“检测—鲁棒性—质量—成本”平衡，而不能只挑一个数字。

## 7. 必做实验三：证明检测不依赖 prompt 内容

这项实验很便宜，却能直接支撑一个容易理解的贡献。

### 想证明什么

同一份最终代码，无论输入记录中放什么 prompt，检测结果都完全相同。

### 怎么做

对每份最终代码构造 5 份输入：

1. 原始 prompt；
2. 空字符串；
3. 另一道题的 prompt；
4. 与代码无关的自然语言；
5. 很长的随机 prompt。

当前接口要求保留 `prompt` 字段，因此实验应替换字段内容，而不是直接删除字段。另做一个精简实验接口或离线脚本，只传最终代码，验证结果仍然一致。

### 需要报告什么

- 每份代码在不同 prompt 下的分数差；
- 最终判断是否发生变化；
- 证据数量和“证据不足”状态是否变化；
- 检测运行时是否加载生成模型。

### 什么结果有说服力

在不同 prompt 内容下，分数、证据数量和最终判断应完全相同。最好用自动化测试给出“最大分数差为 0”，而不仅是平均值接近。

### 还可以补一个更强的展示

把同一批最终代码复制到一台没有生成模型、没有生成日志的机器上，只保留检测器、语义编码器和密钥，仍能得到相同结果。这能直观展示“最终代码独立检测”。

## 8. 必做实验四：分层鲁棒性实验

这是最能提高论文价值的实验，也是最需要认真设计的部分。

### 8.1 基本原则

鲁棒性实验必须同时满足 3 条：

- 修改前后功能保持一致；
- 修改强度可以量化；
- WFCLLM 与基线面对完全相同的修改。

如果改写后代码已经不能运行，那么水印是否保留没有实际意义。因此，每个改写样本都要在检测结束后运行原任务测试，功能发生变化的样本单独报告，不能混入主要鲁棒性结果。

### 8.2 建议的 5 层改写

#### 第 0 层：只改变外观

- 自动格式化；
- 改变空格和换行；
- 删除或增加普通注释；
- 改变引号形式；
- 调整数值和字符串的等价写法。

这一层主要检查方法是否会被最简单的编辑破坏。

#### 第 1 层：局部词法修改

- 变量重命名；
- 函数内部临时变量重命名；
- 等价常量表达；
- 调整不影响结果的括号。

这一层最适合比较语义水印与 token 水印的差异。

#### 第 2 层：表达式和接口改写

- `a + a` 与 `2 * a` 等等价表达；
- 不同但等价的标准库调用；
- 条件表达式与普通 `if` 赋值互换；
- 循环与列表推导式互换；
- 拆分或合并局部表达式。

#### 第 3 层：结构改写

- 调整独立语句顺序；
- 增加不影响结果的代码；
- 提前返回与嵌套条件互换；
- 局部循环和控制流重写；
- 提取或内联一个小函数。

这一层会改变更多结构，能够测试水印影响是否局部化。

#### 第 4 层：大模型重构

让代码大模型在明确要求“保持功能不变”的条件下重写代码。至少使用 2 种不同重构提示，并限制修改预算，避免生成完全无关的新程序。

这更接近真实攻击，但结果波动较大，建议放在前 4 层规则化实验之后。

### 8.3 每层需要比较什么

对 WFCLLM 和每个基线同时报告：

- 改写前检出率；
- 改写后检出率；
- 检测分数保留比例；
- 保留下来的可检测结构单元比例；
- 修改了多少 token 和多少结构节点；
- 改写后仍通过功能测试的比例；
- “证据不足”的比例是否上升。

### 8.4 什么结果有说服力

最关键的不是 WFCLLM 在所有强攻击下都毫无下降，而是出现符合机制解释的趋势：

- 外观变化和变量重命名对 WFCLLM 的影响较小；
- 纯 token 方法在这些修改后下降更明显；
- 局部结构修改主要影响附近证据，而不是让全部证据同时消失；
- 随着修改强度增加，各方法逐步下降，但 WFCLLM 的下降更慢；
- 功能保持的样本中，WFCLLM 的改写后检出率或分数保留显著优于基线。

### 8.5 建议的核心图

横轴是修改强度，纵轴是改写后的检出率或分数保留比例。每种方法一条曲线。读者应能一眼看出：代码改得越多，谁的水印消失得更快。

## 9. 必做实验五：组件删除实验

组件删除实验也叫消融实验。它的目标是回答“真正起作用的是哪一部分”。

### 9.1 建议比较的版本

| 版本 | 保留内容 | 想回答的问题 |
| --- | --- | --- |
| 无水印 | 普通生成 | 检测器的基础误报水平是多少？ |
| 无回退 | 只检测语义命中，不重新生成 | 回退搜索是否真的增加水印证据？ |
| 单次生成 | 只生成 1 个完整候选 | 多次完整生成的选择带来多少提升？ |
| 不使用结构边界 | 使用固定长度文本片段或简单连续窗口 | 代码结构边界是否必要？ |
| 普通语义编码器 | 不专门学习等价代码接近 | 鲁棒语义训练是否必要？ |
| 不使用父结构定位 | 不区分代码单位所处结构 | 结构信息是否帮助密钥定位和检测？ |
| 完整 WFCLLM | 保留全部核心组件 | 最终方法效果是多少？ |

某个版本如果当前实现成本很高，可以先做最接近的可控替代，但要说明替代版本与目标问题的关系。

### 9.2 每个版本要同时看 4 个方面

- 干净代码检测；
- 改写后检测；
- pass@1；
- 生成成本。

只看检测分数可能会得出错误结论。例如，增加重试当然可能提高水印，但如果成本增长 10 倍或代码质量明显下降，就不能说它是有效设计。

### 9.3 最关键的预期关系

- 去掉回退后，水印证据和检出率应下降；
- 去掉结构边界后，干净检测可能仍存在，但改写鲁棒性应更差；
- 普通编码器可能在原始代码上接近，但在变量重命名和等价改写后下降更大；
- 完整方法应给出最好的综合平衡，而不一定在每一个单独指标上都排名第一。

## 10. 必做实验六：代码质量与生成成本

### 想证明什么

水印不是通过严重破坏代码或无限重试换来的。

### 代码质量要测什么

- pass@1；
- 能否通过语法解析；
- 是否完整结束而不是被截断；
- 平均代码长度；
- 重复代码比例；
- 必要时补充常见代码质量检查，但不要用这些检查控制候选选择。

### 生成成本要测什么

- 每个任务平均生成几次；
- 每个结构单元平均回退几次；
- 额外生成了多少 token；
- 单个任务的平均时间和较慢样本的时间；
- 显存占用；
- 不同重试预算下的检测—质量—成本变化。

### 推荐的预算曲线

把重试预算设为 `0、1、2、3、4` 等几个档位。横轴是额外成本，纵轴分别画检出率和 pass@1。这样可以选择一个“再增加重试已经收益很小”的位置作为正式配置。

### 建议的成功标准

可以预先把“pass@1 相对无水印版本下降不超过 3 个百分点”作为推荐目标，而不是实验结束后再挑一个宽松标准。如果达不到，应如实展示质量—检测权衡，并寻找更合适的重试预算。

## 11. 重要实验七：跨模型和跨数据集验证

### 想证明什么

方法学到的是可迁移的代码水印规律，而不是某个模型、某个数据集或某种代码模板的风格。

### 最小配置

- 数据集至少包括 HumanEval 和 MBPP；
- 生成模型至少包括 2 个不同系列；
- 其中一个模型用于主要开发，另一个只用于迁移验证；
- 检测器设置和阈值校准规则预先固定。

### 可以进一步做的强验证

- 在模型 A 上确定方法参数，在模型 B 上直接生成和检测；
- 在 HumanEval 上确定参数，在 MBPP 上不调参测试；
- 使用不同代码长度和不同题目类型分组；
- 如果资源允许，再增加一种编程语言，但它属于后续扩展，不应阻塞当前论文。

### 什么结果有说服力

不同模型和数据集上的绝对数字可以变化，但核心关系应保持：完整方法优于无回退版本，改写后的水印保留优于 token 基线，prompt 替换不影响结果。

## 12. 重要实验八：短代码与“证据不足”分析

### 想证明什么

检测器在证据太少时选择不判断，是由代码信息量决定的，而不是系统随意放弃困难样本。

### 怎么做

按照最终代码长度或可检测结构单元数量分组，例如：

- 很短：只有 0～2 个可检测窗口；
- 较短：3～5 个；
- 中等：6～10 个；
- 较长：10 个以上。

每组报告：

- 检出率；
- 误报率；
- 平均检测分数；
- “证据不足”比例；
- 改写后还剩多少证据。

### 这项实验能支持什么结论

它能解释为什么短代码更难检测，也能帮助确定最少证据数量。论文可以清楚区分“没有检测到水印”和“代码太短，无法可靠判断”。

## 13. 重要实验九：密钥和安全性检查

### 13.1 错误密钥实验

用正确密钥生成水印，再使用大量错误密钥检测。同一份含水印代码在错误密钥下的检出率应接近设定的误报率。

### 13.2 不同密钥之间的干扰

分别用多个密钥生成代码，检查密钥 A 的检测器是否会把密钥 B 的代码大量误认为自己的水印。

### 13.3 水印移植

把一段含水印代码中的局部片段复制到无水印代码中，观察检测器是否容易被少量片段欺骗。理想情况是：少量移植不足以让整段代码通过检测，除非移植了足够多的有效证据。

### 13.4 有目标的去水印攻击

允许攻击者知道算法但不知道密钥，反复进行功能保持的改写，观察需要修改多少代码才能让检测失败。报告攻击成本，而不只是“成功或失败”。

这些实验主要用于安全讨论和附录，不必全部放在主论文正文，但错误密钥实验应当必做。

## 14. 对照实验必须遵守的公平规则

### 相同的生成任务

所有方法使用同一批题目、同样的 prompt 和可比的生成模型设置。

### 相同的误报条件

主要检出率必须在相同误报率下比较。不能让一个方法容忍 10% 误报，另一个只允许 1%。

### 相同的改写

每份原始代码先产生一份改写版本，再让所有检测器检测同一份代码，避免每个方法面对不同攻击样本。

### 相同的功能检查

所有方法的改写代码都运行同样的测试。功能已经改变的样本单独统计。

### 不使用正确性筛选水印候选

生成时不能先生成很多版本，再用测试用例挑一个正确且水印最强的版本。正式方法只能使用水印证据选择候选。pass@1 必须在所有正式决策结束后测量。

### 多个随机种子

关键结果建议至少运行 3 个随机种子，并报告平均值和波动范围。鲁棒性实验可以对同一份代码生成多种改写，避免结论依赖某一次改写。

## 15. 推荐的实验执行顺序

### 阶段 0：先确认测量链路正确

1. 生成—检测一致性；
2. prompt 替换不变性；
3. 正确密钥与错误密钥检查；
4. 一个小数据集上的阈值和指标复算。

停止条件：如果生成命中无法在最终代码中稳定重现，先修复链路，不进入大规模实验。

### 阶段 1：建立基础结果

1. 无水印版本；
2. 完整 WFCLLM；
3. 最强的 1～2 个基线；
4. HumanEval 上的检测、pass@1 和成本。

停止条件：如果含水印和无水印几乎无法区分，先做组件删除和失败分析，不急着跑所有数据集。

### 阶段 2：证明核心创新

1. 无回退版本；
2. 不使用结构边界的版本；
3. 普通编码器版本；
4. 多次完整生成与单次生成对比；
5. 第 0～2 层鲁棒性实验。

这一阶段决定论文的核心主张是否成立。

### 阶段 3：补齐完整故事

1. 第 3～4 层鲁棒性；
2. 重试预算曲线；
3. MBPP 和第二个生成模型；
4. 短代码与证据不足分析。

### 阶段 4：安全和附录扩展

1. 多密钥干扰；
2. 水印移植；
3. 有目标的去水印攻击；
4. 更多模型、数据集或编程语言。

## 16. 主论文最少需要的结果组合

如果时间和算力有限，至少补齐下面 6 组结果：

1. **主检测表**：WFCLLM、无水印版本和强基线在 HumanEval、MBPP 上的检测结果；
2. **代码质量表**：pass@1、语法正确率和代码完整率；
3. **鲁棒性主图**：格式化、重命名、表达式改写、结构改写后的检出率或分数保留曲线；
4. **核心消融表**：无回退、无结构边界、普通编码器、完整方法；
5. **成本曲线**：重试预算与检测、pass@1、时间之间的关系；
6. **最终代码独立检测检查**：不同 prompt 内容下结果完全一致，并补充错误密钥结果。

这 6 组实验能够形成一个闭环：能写入、能读出、为什么有效、改写后是否保留、代价是多少、是否真的只依赖最终代码。

## 18. 每个创新点最终怎样算被证明

### “结构语义单元是有效载体”

需要看到：完整方法优于无结构边界或普通编码器版本，尤其在等价改写后优势更明显。

### “回退搜索能写入水印”

需要看到：增加合理的回退预算后，最终代码中的可重建命中和检出率上升；收益随预算逐渐饱和；pass@1 没有明显恶化。

### “只依赖最终代码”

需要看到：替换 prompt 内容不会改变任何检测结果；没有生成模型和生成日志时仍能复现同样分数；检测输入会拒绝生成轨迹等额外信息。

### “对等价改写更鲁棒”

需要看到：在功能保持、修改强度相同的条件下，WFCLLM 的改写后检出率或分数保留明显优于 token 基线，并且优势在多个随机种子、多个改写类型上保持。

### “方法具有实际可用性”

需要看到：代码质量下降处于预先设定的可接受范围，重试成本有明确上限，短代码证据不足能够被识别，错误密钥不会大量误报。

## 19. 最需要优先解决的风险

### 风险一：生成端和检测端证据不一致

这是最大风险。优先做逐单元对齐，不要只看最终 AUROC。

### 风险二：干净检测仍然较弱

如果干净检测没有明显超过基线，论文必须依靠“改写后保留更好 + 最终代码独立检测 + 可接受成本”的综合优势，而不能宣传为最强检测器。

### 风险三：鲁棒编码器没有真正学到等价性

如果变量重命名或等价改写就让语义表示大幅变化，应先改进训练数据和编码器，再扩大水印实验。

### 风险四：短代码没有足够证据

需要按证据数量分组，并考虑多粒度窗口。不能只报告整体平均值掩盖短代码失败。

### 风险五：重试带来的收益不抵成本

必须画成本—收益曲线。如果多次完整生成的收益很小，应减少重试，把方法简化到最有价值的部分。

## 20. 最终优先级

### P0：没有这些实验，不宜形成强论文主张

- 生成—检测一致性；
- 干净代码主要检测对比；
- prompt 内容替换不变性；
- 分层鲁棒性；
- 核心组件删除；
- pass@1 与生成成本；
- 正确密钥与错误密钥。

### P1：显著提高论文可信度

- HumanEval 与 MBPP；
- 第二个生成模型；
- 短代码和证据不足分析；
- 多随机种子和统计误差范围；
- 更强的结构改写。

### P2：适合附录或后续工作

- 大模型反复重构攻击；
- 水印移植和伪造；
- 更多数据集和生成模型；
- 多编程语言；
- 长期 Git 提交中的真实重构历史。

## 21. 一句话总结

需要补齐的实验应当共同证明：

> WFCLLM 的结构语义机制确实把可重建的水印写进了最终代码；这种水印不依赖 prompt 和生成日志，在功能保持的代码改写后比纯 token 水印保留得更好，而且没有用不可接受的代码质量和生成成本换取检测效果。
