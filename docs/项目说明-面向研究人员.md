# WFCLLM 项目说明：面向新研究人员

本文档用于向不了解本项目的研究人员介绍 WFCLLM。文档分为两个版本：

- 精简版：用于快速讲清楚项目目的、核心原理、整体逻辑和运行流程。
- 详细版：用于说明当前工程实现状态、模块划分、关键技术细节和后续研究关注点。

## 一、精简版

### 1. 项目一句话介绍

WFCLLM 是一个面向代码大语言模型的生成时双通道水印系统。当前实现同时使用语义通道和 token 词法通道，在代码生成过程中嵌入不可见、可统计验证、对一定代码变换具有鲁棒性的水印，从而判断一段代码是否由指定系统生成。

这里的水印不是简单地修改变量名或插入特殊字符串。当前系统有两条互补路径：语义通道让生成代码块的语义表示在统计上偏向密钥决定的目标区域；token 词法通道在生成时对可见 token 分布施加受密钥控制的轻量偏置。检测时，两条通道可以单独给出结果，也可以融合成联合判决。

### 2. 为什么要做这个项目

随着 Code LLM 被广泛用于代码生成，研究和应用上都会遇到一个问题：如何判断一段代码是否可能来自某个代码生成模型或某个受控生成系统。

普通文本水印通常依赖 token 分布。例如让某些 token 更容易出现，检测时统计这些 token 是否异常偏多。但代码有几个特殊点：

1. 代码需要语法正确、能运行，不能随意改变 token。
2. 代码有 AST 结构，语句块之间有明确的语义边界。
3. 攻击者可以做等价变换，比如变量重命名、格式化、控制流改写、表达式替换。
4. 只依赖表层 token 的水印可能很容易被格式化或重写削弱。

所以本项目的核心思路是：利用代码的 AST 语句块结构，在生成过程中对每个语句块进行语义级检查，通过拒绝采样让最终代码块的语义向量落入密钥指定的目标区域。

### 3. 核心思想

整个项目围绕四个对象展开：

1. 语句块：代码不是按整段文本处理，而是按 AST 中的 statement block 处理。语句块是水印嵌入和检测的基本单位。
2. 语义编码器：项目训练或加载一个代码语义编码器，把一个代码块映射成向量。目标是让等价变换后的代码块向量仍然接近，语义变化的代码块向量明显不同。
3. 密钥控制的目标区域：给定一个 secret key 和语句块的 AST 局部结构，系统可以确定一组伪随机目标方向或 LSH 目标区域。只有密钥持有者才能重建这个目标。
4. token 词法通道：在语义通道之外，系统还训练和加载一个 token-channel 模型，在生成时对特定候选 token 施加 green-list 偏置，并在检测端通过 replay 方式统计词法命中情况。

生成时，系统同时维护两条水印路径。语义通道在模型每生成出一个完整的简单语句块后暂停并检查：

```text
当前代码块 -> 语义编码器 -> 语义向量 -> 密钥派生目标区域 -> 是否命中
```

如果命中，保留该语句块，继续生成。如果不命中，就回滚这个语句块并让 LLM 重新生成，最多重试若干次。这就是拒绝采样。

词法通道则在逐 token 生成时根据上下文、密钥和 token-channel 模型决定是否对候选 token 进行偏置。检测时，不需要原始代码。只要有待测代码和相同密钥，就可以重新解析 AST、重放 token-channel 规则，分别得到语义检测分数和词法检测分数，再进行联合判决。

### 4. 三阶段流程

#### 阶段一：训练鲁棒语义编码器

输入是代码数据集，例如 HumanEval、MBPP。系统先从代码中切分语句块，然后构造三元组：

- anchor：原始代码块。
- positive：语义等价变换后的代码块，例如变量重命名、格式变化、部分等价控制流变换。
- negative：语义不等价的代码块，例如随机其他代码块或破坏逻辑的变异代码。

然后用对比学习训练 CodeT5 编码器，使其学习“语义相同则向量接近，语义不同则向量分离”。

输出是语义编码器 E。

#### 阶段二：生成时嵌入水印

输入是 prompt、代码生成 LLM、语义编码器 E、token-channel 模型和 secret key。

流程如下：

1. LLM 开始逐 token 生成代码。
2. token 词法通道根据上下文、密钥和 green-list 规则对部分候选 token 施加偏置。
3. 系统实时维护生成文本并解析 AST。
4. 一旦发现一个完整的 simple statement block，就取出这个代码块。
5. 用编码器 E 得到语义向量。
6. 根据 secret key、语句块结构和 LSH 参数得到语义目标区域。
7. 如果语义向量命中目标区域，则保留。
8. 如果没有命中，则回滚并重新生成该块。
9. 对整个数据集重复这个过程，输出含水印代码 JSONL。

生成端输出不仅包含 generated_code，还包含嵌入统计信息、block metadata、水印参数和诊断信息，方便后续检测和实验分析。

#### 阶段三：提取与验证水印

输入是待测代码、同一个 secret key、语义编码器 E 和 token-channel 模型。

流程如下：

1. 解析待测代码，重新切分语句块。
2. 对每个 simple block 计算语义向量。
3. 用 secret key 重建该块的目标 LSH 区域。
4. 判断每个块是否命中语义目标。
5. 重放 token-channel 词法检测，统计 green token 命中情况。
6. 分别得到语义 Z 分数和词法检测分数。
7. 根据配置进行 semantic-only、lexical-only 或 dual-channel 联合判决。
8. 如果联合检测分数超过阈值，则判断为含水印代码。

在自然未加水印的代码中，每个块命中目标区域的概率应该接近随机基线。含水印代码由于生成时被拒绝采样筛选过，命中率会显著偏高。

### 5. 当前项目整体流程图

```text
数据集 / prompt
    |
    v
阶段一：语义编码器训练
    代码 -> AST 语句块 -> 正负样本构造 -> CodeT5 对比学习 -> 语义编码器 E
    |
    v
阶段二：水印嵌入
    prompt + LLM + E + token-channel + secret key
    -> 逐 token 生成
    -> token 词法通道施加 green-list 偏置
    -> AST simple block 拦截
    -> LSH 语义检验
    -> 失败则回滚重采样
    -> 输出含水印代码 JSONL
    |
    v
阶段三：水印检测
    待测代码 + E + token-channel + secret key
    -> AST 语句块提取
    -> 语义向量打分
    -> token-channel replay 词法打分
    -> 统计检验 / 双通道联合检测
    -> 输出 details JSONL + summary JSON
```

### 6. 给新研究人员的理解重点

理解这个项目时，可以抓住四个关键词：

1. 语句块：水印不是作用在整段代码，也不是单纯作用在 token，而是作用在 AST 语句块。
2. 语义通道：代码块先被编码成语义向量，再判断是否符合密钥派生的 LSH 水印目标。
3. 词法通道：生成时对 token 分布施加受密钥控制的轻量偏置，检测时通过 replay 统计 green token 信号。
4. 联合检测：最终不是只看单个块或单个 token，而是融合语义块命中率和词法命中率，判断整体统计显著性。

## 二、详细版

### 1. 项目定位

项目名称：WFCLLM，全称可理解为 WaterMark for Code LLM。

研究主题：基于语句块语义特征与 token 词法偏置的生成时双通道代码水印。

项目目标是在代码大模型生成代码的过程中嵌入可检测水印。当前实现采用 dual-channel 作为默认运行模式：语义通道负责 AST 语句块级别的鲁棒语义信号，token 词法通道负责 token 级别的密钥控制偏置信号，两者在检测端融合为联合判决。系统希望满足以下要求：

1. 不明显改变代码外观，不插入显式标记。
2. 尽量保持语法正确和功能正确。
3. 检测时不依赖原始代码，即无参考检测。
4. 对格式化、变量重命名、部分等价代码变换具备一定鲁棒性。
5. 适合离线环境运行，避免测试和核心流程依赖 HuggingFace Hub 网络访问。

这个项目目前已经从早期实验代码迁移为较完整的工程结构。`experiment/` 目录只作为历史参考，不允许在生产代码 `wfcllm/` 中直接 import。

### 2. 当前工程结构

主要代码位于 `wfcllm/`：

```text
wfcllm/
├── encoder/          # 语义编码器训练、评测、模型定义
├── pretrain/         # 预训练阶段编排，包含 encoder 和 lexical 相关预训练入口
├── watermark/        # 生成时水印嵌入核心逻辑
├── extract/          # 水印提取、检测、校准、统计检验
├── datasets/         # HumanEval、MBPP 等本地数据集加载
├── lang/             # 语言适配层，目前重点是 Python
├── common/           # 通用结构，如 block contract、checkpoint、registry
├── evaluation/       # 检测报告、代码执行、benchmark、双通道评估
├── ablation/         # 消融实验 runner、metrics、sweep
├── cli/              # run.py 参数解析、配置解析、阶段 runner
└── orchestration/    # 阶段编排、运行状态、依赖检查
```

入口文件是 `run.py`。它是一个很薄的 shim，实际入口在 `wfcllm.cli.entry:main`，阶段执行逻辑主要由 `wfcllm.cli.runners` 分发。

测试目录为 `tests/`，当前覆盖范围较广，包括：

- AST 解析和语句块契约。
- 正负代码变换规则。
- 编码器配置、数据集、训练、评测。
- 水印生成器、拦截器、重试、回滚、cascade、LSH、gamma、自适应熵。
- 提取检测、校准、对齐、token-channel、联合检测。
- CLI、集成测试、消融实验和评测脚本。

当前仓库中 `wfcllm/` 和 `tests/` 下 Python 文件数量较多，整体已经不是单脚本实验，而是一个分阶段、可测试、可恢复的研究工程。

### 3. 核心算法框架

#### 3.1 语义编码器

语义编码器定义在 `wfcllm/encoder/model.py`。

当前实现基于 CodeT5 encoder：

```text
CodeT5 Encoder -> first-token pooling -> Linear projection -> L2 normalize
```

模型输出是固定维度的 L2 归一化向量，默认维度为 128。这个向量用于后续余弦相似度、投影和 LSH 检验。

编码器支持：

- CodeT5 作为底座模型。
- LoRA 微调，默认开启。
- BF16 加载，默认开启。
- 投影头输出低维语义嵌入。

训练数据采用三元组：

```text
anchor:   原始代码块
positive: 语义等价变换代码块
negative: 随机负样本或破坏性变换代码块
```

训练目标是让：

- anchor 与 positive 的余弦相似度更高。
- anchor 与 negative 的余弦相似度更低。
- 两者之间满足 margin。

这使编码器尽量忽略格式、命名等表层差异，保留执行语义相关信息。

#### 3.2 语句块提取

项目不是以整段文件为水印单位，而是以 AST statement block 为单位。

目前语言适配层位于 `wfcllm/lang/`，重点实现是 Python：

```text
wfcllm/lang/python/parser.py
wfcllm/lang/python/adapter.py
wfcllm/lang/python/transform/
```

代码会被解析为 AST，并提取语句块。系统区分：

- simple block：通常是实际嵌入和检测的主要单位。
- compound block：如循环、条件、函数等复合结构，可用于上下文、层级或 cascade 逻辑。

当前检测端实现已经明确倾向于 simple block：`WatermarkDetector.detect()` 会提取所有 blocks，但实际打分主要使用 simple blocks。

#### 3.3 密钥派生与 LSH 目标空间

水印目标由 secret key 控制。项目中相关模块包括：

```text
wfcllm/watermark/keying.py
wfcllm/watermark/lsh_space.py
wfcllm/watermark/verifier.py
```

核心思想是：

1. 给定 secret key、embedding dimension 和 LSH 参数，构造伪随机超平面或目标空间。
2. 对每个语句块，根据其局部结构信息派生目标区域。
3. 将语义编码器输出的向量投影到 LSH 空间。
4. 判断签名是否落入目标 green region，或是否满足 margin / gamma 要求。

这里的检测不是简单比较某个固定向量，而是基于密钥、结构和 LSH 参数动态重建目标。

当前默认配置中相关参数包括：

```json
{
  "lsh_d": 4,
  "lsh_gamma": 0.75,
  "margin_base": 0.001,
  "margin_alpha": 0.002
}
```

其中：

- `lsh_d` 控制 LSH 签名维度。
- `lsh_gamma` 控制目标区域或命中概率假设。
- `margin_base` 和 `margin_alpha` 用于语义投影的裕度控制。

#### 3.4 生成时双通道嵌入

水印嵌入核心在 `wfcllm/watermark/orchestrator.py`，主要类是 `WatermarkGenerator`。

生成时流程如下：

1. 使用 `GenerationContext` 对 LLM 进行 prompt prefill。
2. LLM 按 token 生成。
3. token-channel runtime 根据当前上下文、密钥和 token-channel 模型决定是否对候选 token 施加 green-list 偏置。
4. 系统在生成过程中维护上下文、KV cache、生成文本和 AST block event。
5. 如果出现 compound block event，则更新 cascade 和上下文状态。
6. 如果出现 simple block event，则进入语义通道处理。
7. 语义通道会调用 retry loop 检验当前块是否满足 LSH 语义水印目标。
8. 如果失败，则回滚该块对应的生成状态，并重新采样。
9. 如果达到最大重试次数仍失败，则记录失败或 fallback。

所以当前嵌入不是单一拒绝采样机制，而是：

```text
token 级偏置嵌入 + 语句块级语义拒绝采样
```

词法通道在 token 生成时持续施加弱信号，语义通道在 AST 语句块闭合后进行强约束筛选。两者作用粒度不同，互为补充。

当前配置中的关键生成参数包括：

```json
{
  "max_retries": 5,
  "temperature": 0.2,
  "top_p": 0.95,
  "top_k": 50,
  "max_new_tokens": 768,
  "repetition_penalty": 1.1
}
```

生成模型默认从本地路径加载，并使用 4-bit quantization：

```text
AutoModelForCausalLM.from_pretrained(..., quantization_config=BitsAndBytesConfig(...), device_map="auto")
```

这说明项目已经考虑了 7B 级代码模型在有限显存下运行的问题。

#### 3.5 自适应 gamma

原始方案中，水印强度可以根据节点熵调整。当前项目已经实现了 adaptive gamma 相关模块：

```text
wfcllm/watermark/adaptive_gamma/
├── calibrate.py
├── entropy.py
├── profile.py
└── schedule.py
```

配置中默认启用：

```json
{
  "adaptive_gamma": {
    "enabled": true,
    "strategy": "piecewise_quantile",
    "profile_path": "data/calibration/humaneval_entropy_profile.json",
    "profile_id": "humaneval_entropy_profile",
    "gamma_min": 0.2,
    "gamma_max": 0.8
  }
}
```

含义是：不同熵水平的语句块使用不同的 gamma 或检测假设。高熵块有更多生成自由度，可以承载更强水印；低熵块生成空间小，强行嵌入容易破坏代码，因此应降低要求。

当前项目会在生成结果中保存 block contract，包括：

- ordinal：块序号。
- block_id：块 ID。
- node_type：AST 节点类型。
- parent_node_type：父节点类型。
- block_text_hash：代码块文本哈希。
- start_line / end_line：行号。
- entropy_units：熵单位。
- gamma_target / k / gamma_effective：自适应 gamma 相关参数。

这个结构定义在 `wfcllm/common/block_contract.py`，用于保证嵌入端和检测端对同一代码块的理解一致。

#### 3.6 当前默认模式：双通道水印

项目当前默认不是 semantic-only，而是 dual-channel。也就是说，语义通道和 token 词法通道都参与水印嵌入和检测。相关目录：

```text
wfcllm/watermark/token_channel/
├── core/
├── runtime/
└── training/
```

配置中默认启用双通道：

```json
{
  "token_channel": {
    "enabled": true,
    "channel_mode": "dual-channel",
    "model_path": "data/models/token-channel",
    "switch_threshold": -10.0,
    "delta": 4.0
  }
}
```

语义通道负责语句块级语义目标；词法通道负责 token 级 green list 或偏置控制。检测端会分别得到：

- semantic result：AST simple block 级语义水印检测结果。
- lexical result：token 词法通道检测结果。
- joint result：融合后的联合检测结果。

联合检测由 `wfcllm.extract.hypothesis.fuse_joint_detection` 处理。当前 extract summary 中会统计：

- semantic z-score。
- lexical z-score。
- green fraction。
- joint score。
- joint prediction rate。

因此，对当前项目的准确描述应是：“以语义通道为结构化鲁棒信号、以 token 词法通道为生成分布信号，并通过 joint detection 融合的双通道代码水印框架。”

#### 3.7 检测与统计检验

检测入口是 `wfcllm/extract/detector.py` 中的 `WatermarkDetector`。

检测流程：

1. 解析代码并提取 statement blocks。
2. 过滤 simple blocks。
3. 对每个 simple block 调用 `BlockScorer` 打语义分。
4. 应用嵌入时保存的 gamma metadata。
5. 调用 `HypothesisTester` 做语义通道统计假设检验。
6. 调用 token-channel lexical replay 检测，统计 token 级 green 命中。
7. 在 dual-channel 模式下融合语义和词法检测结果。
8. 如果输入包含 block contract metadata，则检查嵌入端和提取端 block 是否对齐。

检测输出由 `ExtractPipeline` 写出：

- details JSONL：每个样本一行，包含 z_score、p_value、independent_blocks、hits、joint_score 等。
- summary JSON：汇总 watermark_rate、平均 z-score、置信区间、joint prediction rate、无效样本数量等。

默认检测阈值配置：

```json
{
  "fpr_threshold": 3.0,
  "min_blocks": 3,
  "fpr": 0.05
}
```

如果没有校准语料，系统使用固定 Z 阈值。如果提供负样本语料，则可以通过 calibration corpus 自动校准 FPR threshold，使阈值更贴合当前模型、数据集和参数设置。

#### 3.8 负样本语料与阈值校准

项目支持生成负样本语料，即同一 LLM 不加水印直接生成的代码。相关入口包括：

```text
run.py --phase generate-negative
scripts/generate_negative_corpus.py
```

检测阶段可以传入：

```bash
python run.py --phase extract \
  --secret-key mysecret \
  --calibration-corpus data/negative_corpus.jsonl \
  --fpr 0.01
```

校准逻辑会读取负样本的检测分布，选择满足目标 FPR 的阈值。双通道模式下，还会对 joint threshold 进行校准。

这对研究实验很重要，因为实际 false positive rate 会受到数据集、LLM、tokenizer、语义编码器、LSH 参数和 token-channel 参数共同影响。

### 4. 运行方式

项目没有单独的 build system，主入口是 `run.py`。

查看阶段状态：

```bash
conda run -n WFCLLM python run.py --status
```

运行完整主流程：

```bash
conda run -n WFCLLM python run.py
```

单独训练语义编码器：

```bash
conda run -n WFCLLM python run.py --phase encoder
```

单独运行水印生成：

```bash
conda run -n WFCLLM python run.py --phase watermark \
  --config configs/base_config.json \
  --lm-model-path data/models/deepseek-coder-7b-instruct/deepseek-ai/deepseek-coder-7b-instruct-v1___5 \
  --secret-key 1010 \
  --dataset humaneval
```

单独运行水印提取：

```bash
conda run -n WFCLLM python run.py --phase extract \
  --config configs/base_config.json \
  --secret-key 1010 \
  --input-file data/watermarked/<your_watermarked_file>.jsonl
```

生成负样本语料：

```bash
conda run -n WFCLLM python run.py --phase generate-negative \
  --config configs/base_config.json
```

训练 token-channel：

```bash
conda run -n WFCLLM python run.py --phase token-channel-train \
  --config configs/base_config.json
```

项目要求使用 Conda 环境 `WFCLLM`，不要在 base 环境运行项目代码。

### 6. 当前配置状态

主配置文件是：

```text
configs/base_config.json
```

它包含五类配置：

1. `encoder`：语义编码器训练参数。
2. `watermark`：生成时水印嵌入参数。
3. `extract`：水印检测与统计参数。
4. `generate_negative`：负样本语料生成参数。
5. `token_channel_train`：token-channel 训练参数。

当前默认配置体现出几个状态：

- 编码器底座是 CodeT5-base。
- 语义嵌入维度是 128。
- LoRA 和 BF16 默认开启。
- 水印生成使用本地 DeepSeek-Coder 7B instruct 路径。
- LSH 维度 `lsh_d=4`。
- 语义通道默认配合 adaptive gamma。
- token-channel 默认启用，并采用 dual-channel。
- 检测端默认也启用 dual-channel 和 adaptive detection。
- 负样本校准语料默认路径是 `data/negative_corpus.jsonl`。

### 8. 当前实现和原始方案的差异

原始设计文档描述的是三阶段语义水印：

```text
语义编码器训练 -> AST 生成时拦截与语义水印嵌入 -> 无参考统计检测
```

当前工程实现在此基础上已经转为双通道框架，并增加了多项能力：

1. LSH 改进：不只是单方向投影，而是使用 LSH 空间和 green region。
2. adaptive gamma：根据块熵动态设置检测假设和水印强度。
3. block contract：保存嵌入端和检测端共享的块契约，检查结构对齐。
4. token-channel：作为当前默认启用的词法水印通道。
5. dual-channel joint detection：作为当前默认检测口径，融合语义和词法通道联合判决。
6. negative corpus calibration：基于负样本语料校准 FPR 阈值。
7. checkpoint/resume：watermark 和 extract 阶段支持样本级断点恢复。
8. route-one diagnostics：生成端保存重试、失败原因、cascade 等诊断信息。
9. ablation 和 evaluation：支持更系统的实验比较。

因此，向新研究人员介绍时可以说：项目的原始研究主线来自语句块语义水印，但当前工程状态是一个“语义通道 + token 词法通道 + 联合检测 + 阈值校准”的双通道代码水印研究平台。

### 11. 当前项目的主要研究问题

后续研究可以重点关注以下问题：

1. 语义编码器是否真的对代码等价变换鲁棒。
2. 拒绝采样对代码功能正确率的影响有多大。
3. 不同 LSH 参数下，嵌入率、检测率和误报率如何变化。
4. adaptive gamma 是否显著提升高熵块利用率并减少低熵块破坏。
5. token-channel 与 semantic-channel 的组合是否比单通道更稳健。
6. 对变量重命名、格式化、控制流改写、语义保持重写等攻击的鲁棒性。
7. 负样本校准是否能稳定控制 false positive rate。
8. 生成模型、tokenizer 和数据集变化后，阈值和检测性能是否迁移。

### 12. 一段适合口头介绍的总结

WFCLLM 做的是代码大模型生成时双通道水印。它不是在代码里插入显式标记，而是在生成过程中同时注入两类统计信号：第一类是 AST 语句块级的语义信号，每当 LLM 生成出一个完整语句块，系统就用 CodeT5 语义编码器把这个块变成向量，再用密钥派生的 LSH 目标区域判断它是否携带水印，不满足时回滚并重新生成；第二类是 token 词法信号，系统在逐 token 生成时根据密钥和 token-channel 模型对候选 token 施加 green-list 偏置。检测时，只需要待测代码和密钥，系统会重新解析语句块、重放 token-channel 规则，分别得到语义分数和词法分数，再进行联合判决。当前工程还支持自适应 gamma、负样本校准、断点恢复、消融实验和检测报告，因此它已经是一个较完整的双通道代码水印实验平台。
